# Walk env Implementation Plan (builder 2.6.0)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the fleet give each worktree what it needs to run: copied untracked files, installed dependencies, an environment. Let it run the walk against a **second, isolated dev env** that the fleet starts and stops itself. Also make `/builder:init --update` offer the `agent_walk:` block.

**Architecture:** Five new optional `agent_walk:` config keys (`copy`, `setup`, `env`, `start`, `smoke`) are read by `scripts/config.mjs`. `scripts/fleet.mjs` uses them:
- when it creates a worktree, it runs `copy` and then `setup`;
- `env` goes on every hook and every headless run;
- around each walk-lane feature it runs `reset`, then `start` in the background, polls `smoke`, runs the walk, then kills `start`'s process group and runs `stop`.

The skills learn that when `agent_walk.start` is set, walk readiness under `--agent-walk` never starts or restarts servers.

**Tech Stack:** Node 22 stdlib only; `node:test`; Markdown skills.

**Spec:** the design approved in conversation on 2026-09-26, restated here as the authority:
- `copy: <path>[, <path>…]`: untracked files and dirs, relative to the main checkout. Each one is copied into every NEW worktree at the same relative path. A path that doesn't exist in the main checkout is skipped and noted in the fleet's notes. A copy never overwrites a tracked file in the worktree.
- `setup: <command>`: runs once in each new worktree, after `copy`. If it fails, the feature is `failed` with the reason `setup failed — see <log>`, and output is saved to `logs/<feature>-setup.log`. A reused worktree does not re-run it.
- `env: KEY=VALUE KEY=VALUE …`: whitespace-separated pairs, where the value runs to the next whitespace. Quotes around a value are allowed, e.g. `A="x y"`. `{feature}` in any value is replaced by the feature name. The pairs are merged over `process.env`, with `CLAUDE_PROJECT_DIR` still removed. They are passed to `setup`, `reset`, `start`, `smoke`, `stop` and every `claude -p` child, in both lanes.
- `start: <command>`: a long-running dev env. For each walk-lane feature, after `reset`: spawn `start` detached in the worktree, with output to `logs/<feature>-start.log` and its pgid recorded on the feature as `startPgid`. Then poll `smoke`. After the feature's walk-lane runs end, for any reason including a park, a failure or `stopAll`, kill the process group with `SIGTERM`, then `SIGKILL` after 5 s if it's still alive. Then run `stop` if set.
- `smoke: <command>`: polled every 2 s, for up to `FLEET_SMOKE_TIMEOUT_MS` (default 300000). The env is up at the first exit 0. If it never succeeds, or `start` exits first, the feature is **parked** with `walk env didn't come up — see <start log>`. `smoke` without `start` is ignored. `start` without `smoke` waits 10 s and proceeds.
- The stale-lock takeover also kills any recorded `startPgid`.
- A placeholder in any of the new keys makes the whole block unconfigured, as today.

## Global Constraints

- No dependencies; Node stdlib and POSIX shell only. The plugin names no project, tool or framework.
- Default behaviour is unchanged: with no new keys, the fleet behaves exactly as 2.5.0.
- `/builder:signoff` stays `disable-model-invocation: true`, and nothing here touches the PR lock.
- Test command: `node --test 'scripts/test/*.test.mjs'`. Also `scripts/workspace --self-test` and `claude plugin validate .`.
- Commits: conventional, with the trailer exactly `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Version 2.6.0 (minor: optional keys).

## Review Focus

1. **A walk env left running after a park, failure or signal.** It would hold the ports and break the next feature's walk. Expected: `start`'s group is always killed.
2. **`env` must reach the `claude -p` children and the hooks, and must never re-add `CLAUDE_PROJECT_DIR`.**
3. **A `copy` that overwrites a tracked file in the worktree**, e.g. `copy: package.json`. Expected: it is skipped and noted.
4. **`smoke` polling that never ends** when `start` crashes at once. Expected: park immediately with the start log path.
5. **`setup` re-running on every fleet run** for a reused worktree. Expected: it runs once, only at worktree creation.

**Interfaces:**
- Produces: `cfg.agentWalk` gains `copy: string[]` (split on commas and trimmed, empties dropped; `[]` when absent), `setup: string|null`, `env: Record<string,string>` (`{}` when absent), `start: string|null` and `smoke: string|null`. The existing keys are unchanged.
- Also exported: `parseEnvPairs(s: string) → Record<string,string>`. It splits on whitespace outside double quotes, and each token splits at its first `=`. Surrounding double quotes are stripped from a value. A token with no `=` or an empty key throws `Error('agent_walk.env: "<token>" is not KEY=VALUE')`. `{feature}` is NOT substituted here; the fleet does that per feature.

### Task 2: The fleet prepares worktrees and runs the walk env

**Files:** modify `scripts/fleet.mjs`; test `scripts/test/fleet.test.mjs`; extend `scripts/test/fixtures/stub-claude.mjs` if needed.

**Interfaces:**
- Consumes: Task 1's `cfg.agentWalk.{copy,setup,env,start,smoke}`.
- Behaviour: as in the Spec bullets above.
- Implementation notes:
  - Build one `envFor(feature)` that returns the child env: `process.env`, minus `CLAUDE_PROJECT_DIR`, plus `AW.env` with `{feature}` substituted. Use it in `runClaude` and in `hook()`. `hook` now takes the feature.
  - Run `copy` and `setup` only inside `ensureWorktree`, on the branch that creates a new worktree. On a copy that would overwrite a tracked file, check `git ls-files --error-unmatch` in the worktree, skip, and note it.
  - The walk env lifecycle lives in `walkOne`, around `drive(feature,'walk')`, in the existing `try/finally`. Start it after `reset` succeeds. If `smoke` fails, park and skip `drive`. In `finally`, kill the start group, then `stop`.
  - `stopAll` also kills any feature's `startPgid`.
  - The poll loop must be async and non-blocking, not `execSync` in a loop that blocks forever. Use `spawn` or `execFile` with a per-attempt timeout of about 10 s.
  - Env overrides for tests: `FLEET_SMOKE_TIMEOUT_MS` and `FLEET_SMOKE_INTERVAL_MS` (default 2000).
- Tests: each goes through the existing `makeRepo`/`runFleet` helpers; extend `makeRepo` to take extra `agent_walk` lines.
  1. `copy` puts an untracked file from the main checkout into the worktree; a missing source path is noted in STATUS.md.
  2. `copy` never overwrites a tracked file.
  3. `setup` runs once per new worktree, and not again on a re-run with the worktree reused (count with a file-append command).
  4. `setup` failure → the feature is `failed`, naming the setup log.
  5. `env` reaches the claude child: the stub logs `$WALK_MARK`, set via `env: WALK_MARK=x-{feature}`, and the assertion expects `x-<feature>`. `CLAUDE_PROJECT_DIR` is still absent.
  6. `env` reaches a hook: `reset: sh -c 'echo $WALK_MARK > reset-env'`.
  7. `start` + `smoke`:
     - `start` is a small node script that listens on a port given in `env` and writes its pid to a file;
     - `smoke` checks that port;
     - the happy-path scenario is done;
     - after the fleet exits, the start pid is gone.
  8. `start` killed even on park: same as 7, with the scenario ending in `BLOCK:`; the start pid is gone afterwards.
  9. `smoke` never succeeds: with `FLEET_SMOKE_TIMEOUT_MS=1500`, the feature is parked with `walk env didn't come up`, and no walk-lane claude run happened.
  10. `start` exits at once: parked promptly, well under the smoke timeout.
- [ ] Write the tests, see them fail, implement, see them pass, then run the full suite. Make sure no stray processes remain (`pgrep` for the test's start script).
