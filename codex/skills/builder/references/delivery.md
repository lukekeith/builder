# Final proof and local delivery

## Walk and sign-off

**What the walk covers** follows the plan's `walk` lever: `full` walks the whole acceptance script and the cross-app end-to-end walk; `risk` walks the `[risk]` items and the cross-app steps; `none` walks nothing: record that plainly — *no walk; not human-tested, not agent-walked* — and the delivery report says the same, never "agent-tested". Keep walks lean:

- **One app in scope → the verification script is the walk.** Write no cross-app section repeating it; per-app test items are the verifier's to prove.
- **Walk by screen** — every item on one screen in one visit, from one launch of the app, not a fresh launch per item.
- **A re-walk covers only what the fix changed** — the items that did not pass, plus any passed item the fix's diff touches; every other pass is carried with its evidence.
- **The walker runs no tests.** It judges the running app; a build it ran can take the walk environment down. Suites that need the running app say so in the `verify:` block (`needs:`), and the verifier leases that environment for them itself.

**The merge is tested beside the walk.** When the walk starts — the agent's or the owner's — run `node <plugin>/scripts/lifecycle.mjs prepare <feature>` (below): the verifier tests the feature merged onto the target while the walk runs, so neither waits on the other.

Prepare the running environment using the selected config's ownership rules. A feature's walk applies its migrations to its own isolated database, never the shared dev database; the dev database receives them at landing (below). Migrations, ports, databases, local secrets and services must stay isolated from other worktrees when running parallel builds. Green tests against a test database do not prove the dev environment runs the feature. Run the readiness/smoke checks and then exercise SPEC's final integrated acceptance.

When the user reserves a personal walk, present concrete steps and wait for their actual report. "Go" or "tests passed" never becomes human sign-off. Otherwise use authorized agent verification where possible and record **agent-tested, not human-tested**. If UI tools or required real dependencies are unavailable, record incomplete operational proof and its next action. Do not label simulated behavior as live acceptance.

Record each acceptance ID with environment, action, observed result, SHA, and evidence location. A prior agent walk may also establish cross-app acceptance when it exercised those exact acceptance IDs on the same code and relevant environment. Cite its report and label the proof reused; run uncovered scenarios rather than repeat the entire walk. Any affected code, configuration, dependency or external-state change invalidates that proof. A failed walk creates scoped fixes, followed by review and a re-walk of affected scenarios. Human and agent sign-off provenance remain separate. A hold names the owner's exact reason and required release condition; never clear it merely because checks are green.

## Feature verification

Resolve final-review blockers, complete the required acceptance proof, and commit tracked spec/plan/ledger/handoff evidence under the project's commit policy. Verify the final clean feature HEAD: the verifier's phase tier must be green **at that sha** — `verify.mjs verdict <branch> --tier phase` names the sha it ran at; when it is not HEAD, request the phase tier again and wait (execution.md §Phase close, red and env-broken handled the same way). Require fresh execution for live/environment-sensitive proof. Missing required proof prevents verified state.

Record the exact verified feature HEAD via lifecycle checkpoint (persistence.md). Never make unrelated changes after that claim; changes require re-verification.

**READY = the merge tier green + the walk passed.** The merge tier's verdict holds for HEAD when it tested HEAD, or when every commit since touches only the feature registry (walk results, the manifest, the SPEC) — those carry; any other change is tested again.

## Land through the merge queue

Local delivery targets **the recorded targetBranch**, falling back to originBranch for legacy metadata. It was chosen at start using explicit --into or configured merge_into/base_branch, with the starting branch as the unconfigured fallback. Never infer a new target from the current checkout. Until the merge commit exists, say the feature is **ready to land on `<target>`** — never "landed" or "shipped into" it.

1. Check existing merge authorization, holds/manual policies, and target branch requirements. If the host requires a reviewed PR, prepare the verified result and its review description; do not bypass that rule. User instructions explicitly changing the rule take precedence. Default Builder delivery authorizes a local merge only; no push/PR/publish is implicit.
2. **Ask for the merge.** `node <plugin>/scripts/lifecycle.mjs prepare <feature>` — from built on, so the walk runs beside it. It requires a clean, unpaused feature and an idle target, then asks the verifier's merge tier to test the feature merged onto the target's current tip, **held**: nothing lands until deliver. It returns the request id, and `overlap` — the files where the owner's uncommitted changes in the target checkout meet the feature's (below). Asking again for the same feature and target tip reuses the request. A target checked out in another linked worktree is refused before anything is asked: the verifier lands only into the main checkout or a branch checked out nowhere; tell the owner which worktree to switch, or leave it.
3. **Wait for the verdict** when the walk is done: `node <plugin>/scripts/verify/verify.mjs wait <request> --in <host-repo>` (exit 75 → call it again; 0 green · 1 red · 3 env-broken · 4 conflict). It is the landing's only wait.
4. **Deliver.** `node <plugin>/scripts/lifecycle.mjs deliver <feature>` after the verified checkpoint (persistence.md) and any human walk at exact HEAD. It lands the held green merge by compare-and-swap through the verifier (`release`, or `carry` when only registry commits came after the tested sha), so what lands is exactly the commit every suite ran on. Its `status`:
   - `landed` (exit 0) — the merge commit is on the target; go on to step 5.
   - `testing` (exit 75) — still running, or asked again because the target or the feature moved since it was tested (`why`); wait on the new `request`, then deliver again. Nothing landed.
   - `conflict` (exit 4) — the merge conflicts in `files`. Merge the target into the feature worktree, resolve those files following the spec and the latest target, commit, run the phase tier, checkpoint verified again, then prepare. Record any consequential decision.
   - `red` or `env-broken` (exit 1) — `summary` is the verifier's verdict: a regression is fixed in the feature (execution.md's fix loop), an environment the tests could not run in is fixed first; then verify again and prepare.
   - `needs-you` (exit 3) — the owner's uncommitted changes in the target checkout overlap the feature: ask them (§A landing that needs you). Nothing of theirs was touched.
5. Read the delivery result's `landing`: the migration files the feature added under the config's Walk readiness `migrations:` directory. With `apply_mode: agent` and only additive migrations, deliver already ran `apply:` then `regenerate:` in the target checkout (`action: applied`, log path given), because a dev server there may already be running the merged code. Under `ask`/`human`, for a migration that drops or rewrites data (non-SQL migrations are judged by their forward half; any drop, alter, rename or raw execute counts), a target checked out nowhere, or a failed command, it ran nothing further and `note` names the exact command for the owner; report it verbatim. Under `ask`/`human` with a Walk readiness `pending:` command, deliver asked it in the target checkout: exit 0 means the dev DB already has them (`action: none`, nothing to report); non-zero says it is behind. Without `pending:` the note says the dev DB *may* be behind — git only knows the files landed. `applied-dirty` (or a failure with `dirty` files) means the commands changed files in the target checkout — only those are named, never the owner's own uncommitted work: report them; the owner commits or restores them. The landing itself stands either way. Then read `wrapUp`: the steps Walk readiness names for the target checkout's running dev env — `restart:`, `fixtures:`, then `smoke:` — in that order. Offer them in **one** question (what each does, and that they touch the owner's dev env), run the chosen ones in the target checkout in order, and stop at the first that fails, reporting it. Never run them under `--auto` or an agent handoff — list them in the report instead. An empty `wrapUp` asks nothing.
6. Confirm the merged SHA and ancestry and report remaining limitations honestly. Under `--auto` or an agent handoff the report is the review of what was built (SKILL.md §Reviews, not file paths), autopilot rulings marked `(auto)`, and it says plainly that the feature is agent-tested, not human-tested.
7. **A lesson for next time.** If this feature paid a cost the next feature would pay too — a fix round, a red verdict, a failed walk — propose one line for the config's §Standing traps. In a session, ask once; under an agent handoff leave it in the SPEC and the delivery report offers it. Only the owner adds it: the config is theirs.
8. Deliver recorded the landing in history (`history`: its row, or why not — a landed commit without PLAN.md has no plan size). Measured metrics, when the runtime gives them, go in with `deliver --metrics <file>`. Then optional `cleanup <feature>` removes clean worktrees and deletes branches only after proving their tips are ancestors of the landed target (Git branch -D is used when the starting checkout is on another branch); the verifier's own checkouts beside the repo (`<repo>-verify/`) are left alone. Durable common metadata and tracked spec/plan/ledger survive. Preserve required logs and evidence before deleting scratch; keep the worktrees when further manual validation or debugging is requested.

No external mutation occurs unless separately requested or already authorized. Publishing/deployment can be a user-defined delivery stage, with its own concrete proof and rollback requirements; it is not built into the default local lifecycle.

## A landing that needs you

Uncommitted changes in the target checkout that the feature does not touch are no block: the landing goes around them and they are not mentioned. Changes that **overlap** the feature's files — tracked edits, staged or not, and untracked files where the feature adds the same path — stop the landing before any git write. `prepare` reports them early (`overlap`), while the tests run; `deliver` records the needs-you (`needsYou`: the files, the checkout, the choices) and `$builder status` and `$builder resume` raise it until it is answered.

**Never commit, set aside or discard the owner's changes without their answer**, and never choose for them under `--auto` or an agent handoff: there the feature stays ready to land and the report raises the question. Ask in the session, with the files shown as a review first:

> **`<feature>` is ready to land on `<target>`, but your uncommitted changes there touch files it changes too.**
>
> Your uncommitted changes in `<checkout>` overlap the feature in 2 files:
> - `app/settings.ts` — you changed it; the feature changes it too
> - `app/new-page.tsx` — untracked here; the feature adds it
>
> Nothing of yours has been touched. Builder commits, sets aside or discards none of it without your answer.

Then the picker, each choice explained above it, the recommended one first (`needsYou.choices` is already in that order, the recommended one marked `recommended`, its reason in `needsYou.why`):

- **Set my changes aside, land, put them back** — your changes go into a stash named `builder: before landing <feature>`, the feature lands, and they come back as uncommitted changes. Good for work in progress. If they clash with the feature on the way back, the stash is kept and the clashing files are listed for you to resolve — nothing is dropped or force-resolved.
- **Commit my changes, then land** — your changes are committed on `<target>` with a message you approve, the merged result is tested again on top of your commit, then it lands. Good when your edits are finished work; costs one more run of the merge tier.
- **Leave it for now** — nothing changes; the feature stays ready to land, and `$builder resume <feature>` asks again. Once your changes no longer overlap it, deliver lands it.

**The recommendation**, said above the picker as *I recommend <the choice> — <why>* (Claude's rule): **3 files or fewer → Set my changes aside, land, put them back** — "only a few files: if one clashes when it comes back, it is quick to settle, and nothing of yours is committed under a message you did not write". **More than 3 → Commit my changes, then land** — "with this many files a clash on putting them back is likelier, and it would be left in your checkout; committed first, your work is safe in git and any clash is settled on the feature's side before it lands". Leave it for now is always last.

On **Commit my changes**: show the changed files in that checkout (`git -C <checkout> status --short`) and a proposed message, and ask `A. Commit with this message` · `B. Change the message — say what`. Only on A run `lifecycle.mjs deliver <feature> --commit-mine "<message>"`: it commits every tracked change there plus the untracked files the feature adds (never another untracked file), asks for the merge again (`status: testing`), and the coordinator waits and delivers as in step 3–4. A commit git refuses (a hook) leaves the index as it was.

On **Set my changes aside**: `lifecycle.mjs deliver <feature> --set-aside` stashes everything uncommitted there (untracked included, ignored files never), lands, and applies the stash by its sha. Clean → that stash entry is dropped and `setAside: { clean: true }`. A clash → `setAside` lists the `files`, keeps the stash (`stash` sha, `ref`), and `nextAction` says how to finish: resolve those files, `git add` them, then drop that one stash entry. Report it verbatim. If the landing itself fails after the stash, the changes are put back before deliver returns.

## Archive finished features

`$builder archive [--into <branch>]` keeps the registry to work in flight. A finished folder moves to `<registry>/_archive/<feature>/` keeping only its SPEC.md (PROGRAM.md for a program) under a header saying how it ended; `git log -- <folder>` keeps the PLAN, manifest and ledgers. It works in the checkout of the landing target — merged work is judged there — and needs no feature worktree: its one commit is registry-only and is the owner's confirmed change.

1. **The review.** Run `node <plugin>/scripts/archive.mjs plan [--into <branch>]` and print it verbatim, as markdown: the **Finished** table, the **Old** table, the `Left alone:` line, the `registry:` line. Each row says what the folder is, what it becomes and when it last moved — that table is the review; never ask anyone to open a folder. `registry: clean` → say so and stop. A line saying it is on another branch → relay it, name `git switch <target>`, and stop.
2. **One confirmation**, explained above the picker (SKILL.md §Pickers and lists): **Archive the finished ones** (recommended) — every Finished row: a feature that landed through the merge queue gets `✅ SHIPPED — merged <sha>` (it was verified before it landed); one that says it shipped moves as it reads; one merged by hand and never verified is `✅ CLOSED — not walked` (or `walked, not verified`), never called shipped; leftovers are trimmed. **Those and the old ones** — also every Old row: an abandoned feature is `✖ DROPPED — <reason>` and no longer satisfies a program dependency; a folder with no SPEC moves whole, nothing in it deleted. **Not now** — nothing changes. Why the recommended one: the Finished rows are already in the target or say they shipped; the Old ones are a guess from inactivity, so they go only when the owner says so. No Finished rows → offer **Archive the old ones** · **Not now**. A reply naming folders archives exactly those; a reason given for one is its DROPPED reason.
3. **Apply.** `node <plugin>/scripts/archive.mjs apply <path…> [--into <branch>]` with the chosen rows' first column (a bare folder name works too); a folder the owner drops — an Old row or one the plan left in flight — takes `--drop "<name>=<their reason>"` (its bare name) in the same call, so the batch is still one commit (`docs(archive): <n> folders — <names>`). Print each line it prints. A folder that fails half-way is put back as it was. It refuses — nothing changed — off the target branch or while the registry has uncommitted changes; relay the line.
4. **Done.** Run `archive.mjs plan --summary` again and end with `📍 archived <n> — <names> · <the registry: line>`.

It never pushes, never deletes a folder's only docs, and never touches a folder with uncommitted changes, a name the archive already holds, or a feature with a live Codex record (its worktree still there: resume it, or deliver and clean it up, first).
