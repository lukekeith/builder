# Execution, review, and fix loops

Read PLAN and SPEC once to establish the task dependency graph. Before every dispatch, reconcile ledger completion records with their commit ranges. Record a task's BASE before any edits; the BASE recorded before a phase's first task is that **phase's BASE**. Task briefs and raw reports may live under `.builder/<feature>/` with a local ignore file; durable completion, decisions, and summarized proof live in the tracked feature folder.

Resolve the recorded test plan with `profile.mjs --levers <featurePath>` before dispatch. profiles.md defines its levers — how much an agent walks, review, model routing and the human walk. A legacy `profile:`, or a `slice=… end=…` plan written before 6.0, maps onto it; a build under way with neither is Thorough's mapping. Project requirements and mandatory proof remain floors in every plan.

## Tests are the verifier's

Tests are not a lever and not a worker's job. The verifier (`<plugin>/scripts/verify/verify.mjs`, configured by the config's `verify:` block) runs them in the background, each run in its own clean checkout with its own database and ports. Run every `verify.mjs` command from the feature worktree. It has three tiers; a build uses two:

| Tier | When the build asks for it | What runs | Who waits |
|---|---|---|---|
| **commit** | after each task's commit — `verify.mjs request <worktree> HEAD --tier commit` | the `commit` checks and the tests the commits since the branch's last green can reach | nobody; the next task starts at once, and the verdict is read before the next dispatch |
| **phase** | at each phase close — `verify.mjs request <worktree> HEAD --tier phase --since <phase BASE>`, then `verify.mjs wait <id>` | every test the phase's commits can reach, reusing what already passed at this commit, and the `phase` checks | the build — **its only wait** |
| merge | landing (delivery.md) | every suite whole on the target merged with the branch | landing |

A verdict names the sha it ran at and its request id, and lists **regressions** (fail here, pass on the target — the only thing that becomes a fix, each with the commit that introduced it), **flakes**, **known** failures (red on the target too) and newly found **debt**. Flakes, known failures and debt are reported, never fixed in this build. **Env-broken** means the tests never ran (no report, a failed database lease, a missing `verify:` block): it is never red and never a fix, but it is never a pass either. Exit codes: 0 green · 1 red · 3 env-broken · 4 conflict · 5 none · 6 cancelled · 75 still running.

**Fresh** means the verdict's sha is HEAD. A green verdict for an older sha says nothing about HEAD, and a result remembered from earlier in the conversation is not a verdict. Never run a suite by hand beside the verifier or instead of it, and never tell a worker to run the app's whole suite.

## Task loop

1. Select the first startable incomplete task. Generate its exact block with `<plugin>/scripts/task-brief <PLAN> N <absolute-outfile>`. Append applicable SPEC sections, **Contract** (saying whether it is frozen), relevant decisions/findings, project global constraints, companion skill paths, known interface results, and worktree identity. Then run `node <plugin>/scripts/brief.mjs <absolute-outfile> --ledger <featurePath>/ledger.md --root <worktree>`: it appends the config's §Environment landmines verbatim and the ledger's `## env notes`, so never repeat them in your own context for the worker. When an environment fact bites mid-build — a service that does not reload, a tool that must run from one directory, a cache to rebuild first — add it to the ledger's `## env notes` with its remedy written as a step; the next brief carries it. Batch only same-shape mechanical tasks in one app; record each task's status separately.
2. **Before every implementation dispatch, read the latest verdict:** `node <plugin>/scripts/verify/verify.mjs verdict <branch>` (`<branch>` is the feature branch). Exit 75 or 5 means nothing has finished yet — dispatch. A regression is new when its test id is not yet in the ledger for its `introduced by` commit: dispatch a fix against the task that commit belongs to (the ledger maps commits to tasks), reviewed like any other finding, and record `Regression <test id> (introduced by <sha7>): fix dispatched against Task N`. One already in the ledger is in hand — never dispatch it twice; a later verdict that no longer lists it means the fix held. An env-broken verdict at the commit tier blocks nothing; the phase tier decides.
3. Record BASE, selected role/model/effort, current task, and next action before dispatch. Use models.md. Give the worker explicit absolute worktree, brief and report paths. Writers run sequentially in this worktree. Workers read applicable AGENTS.md and project skills, run **only the tests of the code they change plus the type-check**, and report status, changed files, commit range, commands/results, and concerns. Tell the worker how to read its block (planning.md §PLAN.md structure): the listed tests are written with their assertions as given; code the plan pins — exact copy, a migration, the frozen contract, an algorithm, a security mechanism — is implemented as written; every other body is the worker's to write to the Behaviour lines; a real design choice neither the spec nor the tests settle is reported, not invented. Manual-commit policy means stage and stop for its owner; never bypass it via the coordinator.
4. Read the report. DONE proceeds to review; DONE_WITH_CONCERNS requires resolving correctness/scope concerns; NEEDS_CONTEXT gets missing evidence; BLOCKED gets a changed diagnosis, smaller task, or stronger model as appropriate. Do not retry unchanged requests or dismiss a reported escalation.
5. Generate `<plugin>/scripts/review-package BASE HEAD <absolute-diff-file>` for committed changes; never use HEAD~1 for a multi-commit task. For authorized uncommitted/manual-commit work, generate and label both staged and unstaged diffs separately, including untracked files explicitly. When the plan reviews per slice (`review=slice`), an independent reviewer receives the brief, contract, constraints, diff, and report. It returns **spec compliance and code quality** verdicts with severity, file/location, and concrete impact. The implementer's self-review cannot substitute for required independent review. `review=end` (the recommendation) defers independent review to the mandatory whole-feature review and records tasks as awaiting final review; `review=app` reviews each app's tasks once at its phase close; neither fabricates per-task verdicts. `review=slice+second` adds a second independent contract/schema reviewer. Do not ask the reviewer to rerun tests: the verifier runs them.
6. Resolve "cannot verify from diff" requirements using real source/evidence before completion. Critical/Important findings and confirmed spec gaps enter a scoped fix loop. Minor nonblocking observations are recorded for final review. Validate a finding before changing code; do not obey mistaken review mechanically. A conflict with the plan is ruled against SPEC and recorded.
7. Reuse the worker for scoped fixes while useful. Each round records fixes, covering verification, and a scoped re-review of FIX_BASE..HEAD. By round 3, recurring symptoms require root-cause investigation. Rounds 4–5 use a fresh stronger worker. At five rounds, stop repetitive dispatch and diagnose/replan. Contestable or harmless findings may be deferred with an explicit rationale; **real load-bearing defects cannot be waived to declare the build complete**. Continue independent tasks while blocked dependencies wait.
8. Mark a task complete only with commit range (or explicit staged/manual status), the required review verdicts (or explicit awaiting-final status), evidence, and acceptance coverage in ledger.md. Then **request the commit tier** — `node <plugin>/scripts/verify/verify.mjs request <worktree> HEAD --tier commit` (`<worktree>` is the feature worktree's root); it prints a request id and returns at once. Commit durable checkpoint updates with the work when policy permits. Do not amend unrelated/user commits. Advance to the next task without asking whether to continue.

## Phase close — the build's only wait

A phase closes when every task its `## Phases` row lists is complete in the ledger. Then:

1. **Request the phase tier and wait for it.** `node <plugin>/scripts/verify/verify.mjs request <worktree> HEAD --tier phase --since <phase BASE>` prints a request id; `node <plugin>/scripts/verify/verify.mjs wait <id>` blocks up to nine minutes — give that command a timeout of at least ten minutes. Exit 75 means still running: call `wait` again with the same id. In an app configured `commit: manual`, request it on the uncommitted work with `--tree`. Exit 5 or 6 (the request is gone or was cancelled) → request it again.
2. **Green (exit 0)** → the phase can close. Under `review=app`, review the phase's whole diff now (review package from the phase BASE to HEAD), with the fix loop above; each fix is a commit, so request the phase tier again once the loop ends.
3. **Red (exit 1) — the phase does not close.** Each regression becomes a fix dispatch against the task that introduced it, reviewed like any other finding, never a coordinator fix. Then request the phase tier again and wait. A consumer app's phase never starts on a red producer.
4. **Env-broken (exit 3) — the phase does not close either**, because the tests never ran. Read the verdict's `⚠` lines and fix the environment the way the config's `verify:` block expects it — its `setup`, the database its `db.url` names, a check's `cwd` — never by running a suite by hand instead. Then request the phase tier again. If that fix needs a change to the project config (a missing `verify:` block names `$builder init --update`), it is the owner's: stop as a human step with the exact change (persistence.md). **Env-broken a second time → stop.** Write the park record (persistence.md) with the verifier's reason quoted, checkpoint `building` with that next action, and tell the user in plain words: the tests could not run, why (the `⚠` lines), and the way forward — fix that and say go, or `$builder resume <feature>` later. Under an agent handoff it parks the same way, naming its blocker.
5. **Freeze the producer's contract** once the producer app's phase is green: record it in the manifest and tell every later consumer brief the shape is fixed — a mismatch is reported, never worked around.
6. **One ledger line:** `Phase N (<app>): closed — verify phase GREEN <request id> · <sha>`. Start the next phase in the same turn; the go-ahead covered the whole plan.

Cross-app final acceptance is an end-of-build proof, not repeated after every app phase. Shared package changes are the verifier's to follow: it selects every test the changed files can reach, in every app.

## After the last phase

The last phase's green verdict on the last commit is the end's test run; nothing else runs the suites here. Review the whole feature diff once with a judgment model, including SPEC acceptance, frozen contracts, cross-task interfaces, deferred findings, and ledger rulings. One grouped fix wave plus scoped re-review is preferred over one worker per finding. Residual real blockers reopen work; a loop cap limits repetition, not correctness obligations. After the fix wave commits, request the phase tier again and wait: green before the walk means green on the last commit.

Then record built, write the acceptance walk (its scope follows the plan's `walk` lever — delivery.md), and proceed to delivery.md.

## Build here (`build: here`)

The user chose to build it in this session without the ceremony (`$builder resume <feature> --here` or `$builder build <feature> --here`, recorded with `lifecycle.mjs here <feature>`). Spec, alignment, audit, the decisions gate and the plan still run in full; the plan's go-ahead shows the Phases table and proceeds (planning.md). Under `--agent-walk` or an agent handoff, `build: here` is ignored. Then, in the existing feature worktree — Codex isolation is never skipped:

1. **The coordinator works the tasks in order itself.** For each `### Task N`, read its block, the SPEC section it implements, the recipe its `Recipe:` line names, and the config's §Environment landmines; write the test first where behavior changes, see it fail, implement, see it pass. No implementation workers.
2. **One commit per task** following the project's commit rule, naming every staged file. In an app configured `commit: manual`, stage and carry on; list those for their owner at the end.
3. **Tests by the verifier** — after each task's commit, request the commit tier and read `verify.mjs verdict <branch>` before the next task (exit 75 or 5 → nothing yet); at each phase close, request the phase tier with `--since <phase BASE>` and `wait`, exactly as §Phase close says. A red verdict is fixed here, in place, before the next task or phase; env-broken at a phase close is not a pass either, and twice stops with the reason and a way forward.
4. **Keep the ledger to one line per task** (`Task N: done <sha>`) and checkpoint per persistence.md, so a cleared context resumes at the first task without a line.
5. **Skipped:** implementation and reviewer workers, the whole-feature final review, walk readiness, the walk, sign-off and verification. Still freeze a producer contract in the manifest when its phase closes.
6. **After the last task:** checkpoint `built` with next action "Test it yourself, or resume for walk, review, verification and delivery", commit `chore(<feature>): built here — not walked`, and stop. Report `<feature>: built here, not walked — test it yourself; $builder resume <feature> for the full finish`.

A here build is never delivered from this state. The full finish via resume (or an agent handoff) still runs every landing floor in profiles.md before delivery — including the independent whole-feature final review this path skipped, the walk and fresh verification of the merged result. Keep PLAN, ledger, and reports needed for remaining verification. A green phase tier does not establish final integrated acceptance.
