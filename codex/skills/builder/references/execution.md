# Execution, review, and fix loops

Read PLAN and SPEC once to establish the task dependency graph. Before every dispatch, reconcile ledger completion records with their commit ranges. Record a task's BASE before any edits. Task briefs and raw reports may live under `.builder/<feature>/` with a local ignore file; durable completion, decisions, and summarized proof live in the tracked feature folder.

Resolve the recorded profile with profile.mjs before dispatch. profiles.md defines optional testing, review depth, model routing and human-walk requirements. Legacy builds without a profile use Thorough. Project requirements and mandatory proof remain floors in every mode.

## Task loop

1. Select the first startable incomplete task. Generate its exact block with `<plugin>/scripts/task-brief <PLAN> N <absolute-outfile>`. Append applicable SPEC sections, **Contract**, relevant decisions/findings, project global constraints, companion skill paths, known interface results, and worktree identity. Batch only same-shape mechanical tasks in one app; record each task's status separately.
2. Record BASE, selected role/model/effort, current task, and next action before dispatch. Use models.md. Give the worker explicit absolute worktree, brief and report paths. Writers run sequentially in this worktree. Workers read applicable AGENTS.md and project skills, perform focused verification, and report status, changed files, commit range, commands/results, and concerns. Manual-commit policy means stage and stop for its owner; never bypass it via the coordinator.
3. Read the report. DONE proceeds to review; DONE_WITH_CONCERNS requires resolving correctness/scope concerns; NEEDS_CONTEXT gets missing evidence; BLOCKED gets a changed diagnosis, smaller task, or stronger model as appropriate. Do not retry unchanged requests or dismiss a reported escalation.
4. Generate `<plugin>/scripts/review-package BASE HEAD <absolute-diff-file>` for committed changes; never use HEAD~1 for a multi-commit task. For authorized uncommitted/manual-commit work, generate and label both staged and unstaged diffs separately, including untracked files explicitly. For per-task profiles, an independent reviewer receives the brief, contract, constraints, diff, and report. It returns **spec compliance and code quality** verdicts with severity, file/location, and concrete impact. The implementer's self-review cannot substitute for required independent review. A review=final profile defers independent task review to the mandatory whole-feature review and records tasks as awaiting final review; it does not fabricate per-task verdicts. review=per-task+second adds a second independent contract/schema reviewer. Do not ask the reviewer to rerun already recorded unchanged tests.
5. Resolve "cannot verify from diff" requirements using real source/evidence before completion. Critical/Important findings and confirmed spec gaps enter a scoped fix loop. Minor nonblocking observations are recorded for final review. Validate a finding before changing code; do not obey mistaken review mechanically. A conflict with the plan is ruled against SPEC and recorded.
6. Reuse the worker for scoped fixes while useful. Each round records fixes, covering verification, and a scoped re-review of FIX_BASE..HEAD. By round 3, recurring symptoms require root-cause investigation. Rounds 4–5 use a fresh stronger worker. At five rounds, stop repetitive dispatch and diagnose/replan. Contestable or harmless findings may be deferred with an explicit rationale; **real load-bearing defects cannot be waived to declare the build complete**. Continue independent tasks while blocked dependencies wait.
7. Mark a task complete only with commit range (or explicit staged/manual status), the required profile review verdicts (or explicit awaiting-final status), evidence, and acceptance coverage in ledger.md. Commit durable checkpoint updates with the work when policy permits. Do not amend unrelated/user commits. Advance to the next task without asking whether to continue.

## Phase and slice boundaries

At phase close, run the owning app's fast gates via `node <plugin>/scripts/gate.mjs <app>`. Include project-mandated lint, build, stories, guardrails, and tests in configuration; do not assume a typecheck is a production build. Cross-app final acceptance is an end-of-build proof, not repeated after every app phase. Freeze a producer contract after its phase verifies and propagate its exact shape to consumers.

Shared package changes can invalidate other app gates: reason about dependencies rather than assuming untouched app folders are unaffected. The bundled gate memo can reuse green content-identical inputs; report it as **reused**, with original SHA/time. Environment-sensitive or external-state checks and uncertain dependency scope use `--force`/`--whole`. Final integration verification runs fresh against the exact candidate. Never alter known-red baselines merely to pass new violations.

For configured `@delta` gates, establish the baseline against the captured starting code before implementation, from a baseline worktree at targetStartHead (legacy originHead), or the still-unchanged initial feature worktree. `gate.mjs --baseline` stores the measured result for other worktrees. If config must be authored first, create the baseline worktree at targetStartHead (legacy origin-head), supply that verified config there, and run the baseline commands against unchanged app code. Record the baseline SHA and commands. A missing baseline fails; a feature's own measurement must never become its regression allowance. In this port, a flaky match earns one retry of the original gate; a green narrow diagnostic cannot substitute for a failed suite.

After the last phase, review the whole feature diff once with a judgment model, including SPEC acceptance, frozen contracts, cross-task interfaces, deferred findings, and ledger rulings. One grouped fix wave plus scoped re-review is preferred over one worker per finding. Residual real blockers reopen work; a loop cap limits repetition, not correctness obligations.

Then record built, write the acceptance walk, and proceed to delivery.md. Keep PLAN, ledger, and reports needed for remaining verification. A passing task suite does not establish final integrated acceptance.
